# PRD: Personal Data and Nutrition Engine V1

## 1. Document status

- Product: FoodLens
- Scope: Personal data infrastructure, persistent diary, and deterministic nutrition engine
- Status: Proposed for implementation
- Baseline: commit `1f07c8f`
- Target clients: Flutter Android, iOS, and Web
- Target backend: FastAPI and PostgreSQL 17

## 2. Problem statement

FoodLens currently recognizes up to eight visible food components and provides calorie estimates from an in-memory catalog. Diary entries exist only in Flutter memory and disappear after a reload. Nutrition profiles contain calories but not complete macros, source provenance, or version history.

This prevents reliable implementation of goals, reports, favorites, recipes, barcode logging, weight trends, and coaching. V1 must establish a persistent and auditable data foundation before those features are built.

## 3. Product objective

A user must be able to:

1. Open FoodLens without creating an email account.
2. receive an isolated private profile on that device.
3. recognize or manually select multiple food components.
4. review weight and nutrition for each component.
5. assign the meal to breakfast, lunch, dinner, or snack.
6. save, edit, and delete diary entries.
7. close or reload the app and see the same diary data.
8. see deterministic daily totals for calories, protein, carbohydrates, fat, and fiber.
9. delete all personal data associated with the device profile.

## 4. Success criteria

V1 is successful when:

- Diary entries survive app reloads and backend restarts.
- Every persisted record is isolated by profile ownership.
- Nutrition totals are computed from structured values, never generated by the vision model.
- Every published nutrition value has a source, revision, and review state.
- Existing image recognition remains available when persistence is temporarily unavailable.
- Existing QuizLens and other VPS services remain unaffected.
- No meal image is retained after recognition by default.

Initial operational targets:

- `GET /v1/diary/day` p95 latency below 500 ms on the current VPS.
- Nutrition arithmetic test coverage for calories and all four V1 macros.
- Zero cross-profile access in authorization tests.
- Daily database backup with a documented restore test.

## 5. Scope

### 5.1 Included

- Anonymous device profile and secure bearer token.
- Persistent user profile and timezone.
- Persistent diary with meal types.
- Multi-component meal storage.
- Create, read, update, and delete diary operations.
- Calories, protein, carbohydrates, fat, and fiber.
- Structured food, portion, nutrient, and source records.
- Nutrition profile versioning.
- Daily totals.
- User-entered custom foods.
- Data export as JSON.
- Full profile deletion.
- Database migrations and backups.
- Migration of the existing catalog into PostgreSQL.

### 5.2 Explicitly excluded

- Email, phone, social login, and account synchronization across devices.
- AI nutrition coaching.
- Medical or disease-specific recommendations.
- Micronutrients beyond the V1 nutrient set.
- Barcode lookup.
- Voice logging.
- Recipe builder UI.
- Restaurant menu OCR.
- Weight and water tracking.
- PDF and CSV exports.
- Long-term storage of uploaded meal images.
- Automatic use of user corrections as training data.

The schema should leave room for these capabilities, but V1 must not implement them indirectly.

## 6. Identity model

### 6.1 Device profile

On first launch, the client calls `POST /v1/profiles/anonymous`. The backend creates:

- a random profile UUID;
- a random 256-bit bearer token;
- a one-way hash of that token in PostgreSQL.

The plaintext token is returned once and stored in platform secure storage. Flutter Web stores it in browser storage with an explicit warning that clearing browser data removes access to that profile.

All personal endpoints require:

```http
Authorization: Bearer <device-token>
```

The backend must compare a cryptographic token hash and must never log the token.

### 6.2 Limitations

An anonymous device profile is not a recoverable account. V1 must state this clearly in settings. Account linking and multi-device synchronization are a later feature and must not change ownership keys used by diary records.

## 7. User journeys

### 7.1 First launch

1. Client requests an anonymous profile.
2. Client stores the returned token.
3. Client asks for timezone and optional daily calorie target.
4. Dashboard loads today's persisted diary.

### 7.2 Photo logging

1. User selects or captures an image.
2. Vision API returns recognized components and confidence.
3. Client loads canonical food and portion information.
4. User corrects food identity, unit, and weight for each component.
5. User chooses meal type.
6. Client submits one meal containing one or more components.
7. Backend calculates and stores a nutrition snapshot.
8. Client refreshes daily totals.

### 7.3 Manual food

1. User chooses manual entry.
2. User enters a name and nutrition per 100 g.
3. Backend creates a private custom food owned by that profile.
4. Diary component references that custom food.
5. The custom food is available only to its owner.

### 7.4 Edit and delete

- User can edit meal type, timestamp, food, portion, and grams.
- Backend recalculates the complete nutrition snapshot after an edit.
- User can delete a component or the complete meal.
- Empty meals are automatically deleted.

### 7.5 Delete profile

1. User confirms destructive deletion.
2. Backend deletes diary, custom foods, profile settings, and token records in one transaction.
3. Backend returns `204` only after deletion succeeds.
4. Client removes its local token and returns to first launch.

## 8. Nutrition model

### 8.1 V1 nutrients

Each food profile must support values per 100 g for:

- energy: kcal;
- protein: g;
- carbohydrate: g;
- fat: g;
- fiber: g.

Values may be unknown during migration, but the API must represent unknown as `null`, never as zero.

### 8.2 Deterministic calculation

For nutrient $n$ and consumed mass $g$:

$$
N_n = \frac{g}{100} \times V_n
$$

where $V_n$ is the stored nutrient value per 100 g.

For a meal with components $1 \ldots k$:

$$
N_{meal} = \sum_{i=1}^{k} N_i
$$

All calculations use decimal arithmetic in the backend. API display values are rounded only at the response boundary:

- grams: one decimal place;
- calories: one decimal place;
- macros and fiber: one decimal place.

### 8.3 Snapshot rule

Each diary component stores a nutrition snapshot at save time. Future catalog corrections must not silently rewrite historical diary totals. A user-triggered recalculation feature may be added later.

The snapshot records:

- food profile version ID;
- grams;
- kcal, protein, carbohydrate, fat, and fiber;
- uncertainty percentage;
- calculation timestamp.

### 8.4 Uncertainty

Uncertainty is stored per food profile and copied into the diary snapshot. V1 applies the same relative uncertainty to calorie and macro estimates. Unknown nutrient values remain `null` and do not produce a numeric range.

### 8.5 Data provenance

Every canonical nutrition profile requires:

- source name;
- source URL or publication identifier;
- source access date;
- source type;
- review state;
- reviewer note;
- effective version timestamp.

Allowed review states:

```text
draft
source_checked
nutritionist_reviewed
retired
```

Only `source_checked` and `nutritionist_reviewed` profiles may be returned by the production catalog. Existing seed data remains `draft` until reviewed and must be visibly marked as estimated during migration.

## 9. Proposed data model

PostgreSQL is the source of truth. UUID primary keys are generated server-side. All timestamps use timezone-aware UTC.

### 9.1 `profiles`

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `timezone` | text | IANA timezone, default `Asia/Tehran` |
| `locale` | text | Default `fa-IR` |
| `daily_calorie_target` | numeric, nullable | User-adjustable |
| `created_at` | timestamptz | Required |
| `updated_at` | timestamptz | Required |
| `deleted_at` | timestamptz, nullable | Tombstone during deletion workflow |

### 9.2 `profile_tokens`

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `profile_id` | UUID | Foreign key, cascade delete |
| `token_hash` | bytea | Unique; plaintext never stored |
| `created_at` | timestamptz | Required |
| `last_used_at` | timestamptz | Rate-limited updates |
| `revoked_at` | timestamptz, nullable | Revocation support |

### 9.3 `foods`

| Column | Type | Notes |
|---|---|---|
| `id` | text | Stable public ID such as `ghormeh-sabzi` |
| `name_fa` | text | Required |
| `name_en` | text | Required |
| `family` | text | Controlled vocabulary |
| `is_canonical` | boolean | True for shared catalog foods |
| `owner_profile_id` | UUID, nullable | Set only for private custom foods |
| `created_at` | timestamptz | Required |
| `retired_at` | timestamptz, nullable | Never hard-delete canonical foods |

A database constraint enforces exactly one ownership mode:

- canonical food: `is_canonical = true`, owner is null;
- custom food: `is_canonical = false`, owner is present.

### 9.4 `food_aliases`

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `food_id` | text | Foreign key |
| `locale` | text | Example `fa-IR`, `en` |
| `alias` | text | Normalized searchable alias |

Aliases include spelling variants such as `قرمه سبزی`, `قورمه سبزی`, and transliterations. Uniqueness is enforced per locale and normalized alias.

### 9.5 `nutrition_sources`

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `name` | text | Required |
| `source_type` | text | Government DB, label, recipe calculation, expert |
| `reference_url` | text, nullable | HTTPS where applicable |
| `publication_id` | text, nullable | DOI or dataset identifier |
| `accessed_at` | date | Required |
| `licence_note` | text | Required |

### 9.6 `food_profile_versions`

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `food_id` | text | Foreign key |
| `version` | integer | Unique per food |
| `source_id` | UUID | Foreign key |
| `review_state` | text | Controlled state |
| `kcal_per_100g` | numeric, nullable | Non-negative |
| `protein_g_per_100g` | numeric, nullable | Non-negative |
| `carb_g_per_100g` | numeric, nullable | Non-negative |
| `fat_g_per_100g` | numeric, nullable | Non-negative |
| `fiber_g_per_100g` | numeric, nullable | Non-negative |
| `uncertainty_percent` | numeric | Between 0 and 100 |
| `effective_at` | timestamptz | Required |
| `retired_at` | timestamptz, nullable | Only one active published version |

### 9.7 `food_portions`

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `food_id` | text | Foreign key |
| `code` | text | Stable within a food, e.g. `ladle` |
| `name_fa` | text | Required |
| `grams` | numeric | Greater than zero |
| `is_default` | boolean | One default per food |
| `source_id` | UUID, nullable | Portion calibration source |

### 9.8 `meals`

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `profile_id` | UUID | Indexed ownership key |
| `meal_type` | text | `breakfast`, `lunch`, `dinner`, `snack` |
| `eaten_at` | timestamptz | Required |
| `source` | text | `photo`, `manual`, later `barcode` or `voice` |
| `note` | text, nullable | Maximum 500 characters |
| `created_at` | timestamptz | Required |
| `updated_at` | timestamptz | Required |

### 9.9 `meal_components`

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `meal_id` | UUID | Foreign key, cascade delete |
| `food_id` | text | Canonical or owned custom food |
| `food_profile_version_id` | UUID | Version used for calculation |
| `portion_code` | text, nullable | Audit information |
| `quantity` | numeric, nullable | Audit information |
| `grams` | numeric | Greater than zero, max 5000 |
| `recognition_confidence` | numeric, nullable | Between 0 and 1 |
| `kcal_snapshot` | numeric, nullable | Calculated |
| `protein_g_snapshot` | numeric, nullable | Calculated |
| `carb_g_snapshot` | numeric, nullable | Calculated |
| `fat_g_snapshot` | numeric, nullable | Calculated |
| `fiber_g_snapshot` | numeric, nullable | Calculated |
| `uncertainty_percent_snapshot` | numeric | Required |
| `created_at` | timestamptz | Required |
| `updated_at` | timestamptz | Required |

All ownership checks join through `meals.profile_id`. Components must never be addressable without checking meal ownership.

## 10. API contract

All personal endpoint responses use UTF-8 JSON and require authorization.

### 10.1 Profile

```text
POST   /v1/profiles/anonymous
GET    /v1/profile
PATCH  /v1/profile
DELETE /v1/profile
GET    /v1/profile/export
```

`POST /v1/profiles/anonymous` is rate-limited and returns the bearer token once.

### 10.2 Catalog

```text
GET  /v1/foods
GET  /v1/foods/{food_id}
POST /v1/custom-foods
GET  /v1/custom-foods
PATCH /v1/custom-foods/{food_id}
DELETE /v1/custom-foods/{food_id}
```

`GET /v1/foods` remains public for V1 to preserve the current client. It returns published canonical profiles only. Custom food endpoints are private.

The food response adds:

```json
{
  "kcal_per_100g": 165,
  "protein_g_per_100g": 8.2,
  "carb_g_per_100g": 7.1,
  "fat_g_per_100g": 11.5,
  "fiber_g_per_100g": 2.4,
  "nutrition_status": "source_checked",
  "profile_version": 3
}
```

### 10.3 Diary

```text
POST   /v1/meals
GET    /v1/meals/{meal_id}
PATCH  /v1/meals/{meal_id}
DELETE /v1/meals/{meal_id}
GET    /v1/diary/day?date=2026-09-05
GET    /v1/diary/range?from=2026-09-01&to=2026-09-07
POST   /v1/meals/{meal_id}/components
PATCH  /v1/meals/{meal_id}/components/{component_id}
DELETE /v1/meals/{meal_id}/components/{component_id}
```

Date boundaries are interpreted in the profile timezone, then converted to UTC for queries.

### 10.4 Create meal request

```json
{
  "meal_type": "lunch",
  "eaten_at": "2026-09-05T13:15:00+03:30",
  "source": "photo",
  "components": [
    {
      "food_id": "cooked-rice",
      "grams": 250,
      "recognition_confidence": 0.92
    },
    {
      "food_id": "ghormeh-sabzi",
      "grams": 180,
      "recognition_confidence": 0.88
    }
  ]
}
```

The client must not submit calculated calories or macros for canonical foods. The backend selects the current published profile and computes snapshots inside the same transaction.

### 10.5 Daily diary response

```json
{
  "date": "2026-09-05",
  "timezone": "Asia/Tehran",
  "totals": {
    "kcal": 1860.0,
    "protein_g": 92.0,
    "carb_g": 210.0,
    "fat_g": 63.0,
    "fiber_g": 19.0
  },
  "meals": []
}
```

If a nutrient is missing from one or more components, totals include:

```json
{
  "protein_g": null,
  "protein_completeness_percent": 78
}
```

The API must not present an incomplete total as complete.

## 11. Backend architecture

V1 keeps one deployable FastAPI service but separates internal ownership:

```text
app/
  api/
    auth.py
    foods.py
    meals.py
    profiles.py
  domain/
    nutrition.py
    diary.py
  repositories/
    foods.py
    meals.py
    profiles.py
  db/
    models.py
    session.py
  vision/
    providers.py
    schemas.py
```

Required libraries:

- SQLAlchemy 2.x;
- Alembic;
- psycopg 3;
- a cryptographic token hashing library or Python standard cryptographic hash with a server-side pepper;
- Pydantic settings management.

Business calculations remain pure functions under `domain/` and are tested without a database.

## 12. Client changes

Flutter V1 requires:

- secure token storage abstraction;
- API authorization interceptor;
- persisted dashboard loading state;
- meal type selector;
- edit and delete actions;
- daily macro summary;
- previous and next day navigation;
- clear offline/error state;

The client may optimistically update the diary only after retaining a rollback copy. The server response is authoritative.

## 13. Privacy and security

- Uploaded images are held only in process memory and discarded after recognition.
- Request bodies containing images are not logged.
- Bearer tokens are redacted from logs and error reports.
- Tokens are hashed with a server-side pepper stored outside Git.
- Every personal query filters by authenticated profile ID.
- IDs alone never authorize access.
- CORS remains restricted to approved FoodLens origins.
- Profile creation, recognition, and export endpoints are rate-limited.
- Export and deletion events are audit logged without nutrition content.
- PostgreSQL is not exposed on a host port.
- Database credentials remain in the VPS `.env` with mode `600`.
- Backups are encrypted before leaving the VPS.

## 14. Database operations

### 14.1 Deployment constraints

The VPS is shared with QuizLens and other applications. FoodLens storage must use:

- Compose project `foodlens` only;
- no published PostgreSQL port;
- a conservative memory limit initially, proposed 768 MB;
- one PostgreSQL container only after checking available host memory;
- health checks and bounded logs;
- scoped commands using `docker compose -p foodlens`.

The current scaffold requests 3 GB for PostgreSQL and 2 GB for MinIO. Those values must not be enabled unchanged on the shared VPS. MinIO is not needed in V1.

### 14.2 Backup policy

- Daily logical backup with `pg_dump`.
- Seven daily backups and four weekly backups.
- Encrypted storage outside the database volume.
- Monthly restore test into an isolated temporary FoodLens database.
- Restore runbook records duration, row counts, and checksum validation.

## 15. Migration plan

### Phase A: Foundation

1. Add SQLAlchemy, Alembic, and PostgreSQL configuration.
2. Create migrations for profile, catalog, and diary tables.
3. Add repository and transaction boundaries.
4. Add database health information without exposing credentials.
5. Keep current in-memory catalog as a temporary fallback in development only.

### Phase B: Catalog migration

1. Convert the current 87 profiles and portions into a deterministic seed migration.
2. Create a clearly labeled internal seed source.
3. Mark unverified macro values as null.
4. Preserve all existing public food IDs.
5. Verify API response parity for names, calories, uncertainty, and portions.

### Phase C: Identity and diary

1. Implement anonymous profile token lifecycle.
2. Implement meal and component CRUD.
3. Add daily and range totals.
4. Add authorization and cross-profile isolation tests.
5. Connect Flutter diary to the API.

### Phase D: Macro rollout

1. Select an initial set of 20 high-usage foods.
2. Record licensed or public nutrition sources.
3. Add the five V1 nutrients.
4. Review calculations and publish source-checked versions.
5. Expand coverage in batches while exposing completeness.

### Phase E: Production hardening

1. Measure VPS capacity.
2. Enable PostgreSQL with conservative limits.
3. Run migrations as a one-shot scoped task.
4. Deploy API without touching unrelated containers.
5. Verify backup and restore.
6. Monitor database size, latency, errors, and container restarts.

## 16. Acceptance criteria

### Identity

- A new installation can create a profile and receive a token exactly once.
- An invalid, revoked, or missing token receives `401`.
- Profile A cannot read, edit, or delete any record owned by profile B.
- Deleting a profile removes all owned personal records.

### Diary

- A multi-component recognized meal can be saved in one transaction.
- A reload returns the same meal, component order, grams, and snapshots.
- Meal type and eaten time can be edited.
- Components can be added, edited, and deleted.
- Daily boundaries use `Asia/Tehran` correctly, including UTC conversion.

### Nutrition

- Backend results match deterministic fixture calculations within 0.1 units.
- Historical snapshots do not change when a catalog version changes.
- Missing macro values are returned as null with completeness metadata.
- Client-submitted canonical calorie or macro values are ignored or rejected.
- Only published source-checked profiles are served in production.

### Reliability

- API starts cleanly against an empty migrated database.
- Migrations upgrade from the immediately previous production schema.
- Failed meal creation leaves no partial components.
- Recognition still returns a result if diary persistence is unavailable.
- A documented backup can be restored into an isolated database.

### Privacy

- Recognition does not create persistent image files.
- Logs contain no bearer token or image payload.
- JSON export contains all user-owned profile and diary records.
- Full deletion is verifiable by database integration tests.

## 17. Test strategy

- Unit tests for nutrient arithmetic, rounding, and completeness.
- Unit tests for token hashing and verification.
- Repository integration tests against PostgreSQL.
- API tests for CRUD, timezone boundaries, validation, and authorization.
- Explicit two-profile cross-access tests for every personal endpoint.
- Migration tests from empty database and previous revision.
- Flutter API parsing and error-state tests.
- Flutter widget tests for meal type, edit, delete, and persisted reload.
- Production smoke tests for health, CORS, catalog, profile creation, and diary CRUD using a disposable profile.

SQLite must not be used as the only integration-test database because its constraints and numeric behavior differ from PostgreSQL.

## 18. Observability

V1 records metrics without personal food names or free-text notes:

- request count and latency by route;
- HTTP error count;
- database pool saturation;
- transaction failure count;
- recognition provider latency and error count;
- diary save success rate;
- nutrition completeness distribution;
- container health and restart count.

Logs use request IDs. Profile IDs are hashed or omitted from ordinary application logs.

## 19. Product risks and mitigations

| Risk | Mitigation |
|---|---|
| Seed nutrition values are treated as authoritative | Status badge, provenance, publication gate |
| Anonymous token is lost | Clear limitation now; account linking later |
| Cross-user data exposure | Repository ownership filters and adversarial tests |
| PostgreSQL overloads shared VPS | Capacity check, conservative limits, no MinIO |
| Incomplete macro catalog misleads totals | Null values and completeness percentage |
| Catalog updates alter history | Immutable diary snapshots |
| User-entered custom food is inaccurate | Mark as user-provided and private |
| Scope expands into coaching or medical advice | Enforce V1 exclusions |

## 21. Definition of done

V1 is done only when:

- production diary data survives reload and container replacement;
- ownership isolation is tested for every personal endpoint;
- calories and V1 macros are calculated deterministically;
- nutrition source and version are traceable;
- existing multi-component recognition and manual correction remain functional;
- profile export and deletion work end to end;
- backup restore has been successfully rehearsed;
- FoodLens deployment remains isolated and QuizLens health remains unchanged.
